# Лабораторная работа 4

## Часть 1

1. В плохом файле используются `uses: actions/checkout@master`, `uses: actions/setup-python@master`. Теги `@master` могут указывать на нестабильный код разработчика action. При обновлении action пайплайн может сломаться без предупреждения. Нет гарантии воспроизводимости сборок. В хорошем файле это заменено на использование `uses: actions/checkout@v4`, `uses: actions/setup-python@v4`.

2. В плохом файле выполнен хардкод секретов и токенов: `API_KEY: "sk-1234567890abcdef"`, `Authorization: Bearer prod_token_xyz`. Секреты попадают в историю Git, видны в логах CI, доступны всем для просмотра, что нарушает безопасность. В хорошем файле: `${{ secrets.API_KEY }}`, `${{ secrets.DEPLOY_TOKEN }}`. Учетные данные хранятся в зашифрованном хранилище GitHub Secrets.

3. В плохом файле отсутствует кэширование зависимостей pip: `run: pip install -r requirements-dev.txt`, то есть при каждом запуске пайплайна тратится дополнительное время на подгрузку необходимых пакетов. В хорошем файле добавлено кэширование: `cache: 'pip'` в `actions/setup-python@v4`.

4. В плохом файле используется монолитный job:  `monolith-pipeline`. Это делает невозможным запуск независимых задач параллельно, если упал линтер,то не запустится ничего после него. В хорошем файле пять независимых jobs: `lint`, `test`, `security`, `build`, `deploy`. Каждый этап изолирован и это упрощает отладку.

5. В плохом файле тестирование происходит после этапа сборки: сначала `Build package`, а потом `Run tests`. Тратятся ресурсы CI на сборку заведомо битого кода. В хорошем варианте сборка запускается только если все тесты прошли: `test` job выполняется до `build`.

## Часть 2

Хранение секретов в CI/CD переменных репозитория не является хорошей практикой, потому что:

*  Любой пайплайн в репозитории может прочитать секрет.
*  Сложно понять, кто, когда и из какого джоба использовал секрет.
*  Нельзя ввести ограничения, например, доступ только к одному ключу или на определенное время.

Хорошим вариантом является использование HashiCorp Vault, обладающего следующими преимуществами:

*  Можно выдавать токены с ограничением по времени доступа.
*  Логгируется каждый запрос, поэтому известно, кто, когда использовал секрет.
*  Можно разрешить чтение только конкретного пути.
*  В логах применяется маскировка `::add-mask::`, которая гарантирует, что секрет не утечет в вывод.
